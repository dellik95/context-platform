# Context Platform — Token-Efficiency & Search Roadmap

Tracks features aimed at one goal: let Claude Code (and any other agent) get
oriented in a codebase and recall past decisions using as few tokens as
possible, via persistent memory + code-intelligence search instead of
re-reading files from scratch.

Status legend: ✅ done · 🚧 in progress · 📋 planned (not started)

## ✅ Done

- Hybrid search (lexical FTS5 + vector cosine + graph proximity + recency + memory signal), token-budgeted context packs (`ContextPackBuilder`).
- Symbol-level incremental indexing (`SymbolDiffer`), tree-sitter based AST parsing.
- Persistent typed memory (Decision/Discovery/BugFix/Feature/...) with reinforcement/supersession, extracted from session summaries via LLM.
- Session lifecycle: start/prompt/tool-use/end hooks, `SessionSummary` (Completed/Discovered/Decisions/OpenIssues/NextSteps/ChangedFiles).
- Periodic mid-session summarization (`SessionSummaryScheduler`) — a session no longer needs to formally "end" to produce a memory. Batches on event count (not just elapsed time) to avoid noise memories.
- MCP tools exposing all of the above to Claude Code directly (`context_search`, `code_search`, `symbol_search`, `memory_search`, `graph_impact`, etc.) + an installable `context-memory` skill teaching Claude to prefer them over re-deriving context.
- Dashboard (Angular): Projects, Overview, Search, Memories, Sessions, Graph (impact/blast-radius), Settings (provider config, reindex schedule, Claude integration installer, folder-browser project creation), System (live health/job status).
- Live SignalR updates: reindex progress, project stats, session-summary/memory-created activity — panels refresh without polling or reload.
- Cross-platform hook installer (fixed a real bug: was double-registering both `.ps1` and `.sh` commands when a repo was set up from more than one OS, causing every hook to fire twice).
- **Session titles** — `SessionSummary` gets an LLM-generated short descriptive title (git-commit-subject style), shown in the Sessions list/detail instead of a bare timestamp; deterministic non-empty fallback when offline. Live-verified; also fixed a real bug found in verification (`SessionSummaryParser`'s header regex didn't tolerate the markdown headings — `### TITLE:` — this model reliably produces on real-sized sessions, silently discarding the whole parse).
- **Structured memory (Facts)** — `Memory.FactsJson`: 2-5 short, atomic, standalone bullet facts extracted alongside the existing prose `Body`, for when a search result needs to say something useful in very few tokens. Rendered as a bullet list above the body in the Memories tab. Live-verified against real extracted memories.
- **Per-file semantic summary ("file wiki")** — indexing now also generates a short natural-language description of each file (`IFileSummarizer`, no-op under the noop LLM provider) and embeds it as its own searchable chunk (`Chunk.SymbolId = null`). Live-verified: a real reindex produced real file-level search hits with natural-language snippets. File-kind hits render distinctly in the Search tab.
- Fixed `dotnet run`/`dotnet build` never actually serving the Dashboard (`Context.Dashboard.Server.csproj` only copied the built Angular output into `wwwroot/` at publish time, never for a plain run — found live while verifying the three features above).
- **Graph tab visualization** — an actual node/edge graph (vis-network), not just text impact lists: clicking a node shows its connections plus an info panel, "Re-center" re-fetches the neighborhood around the clicked node. Live-verified via Playwright against the real dashboard+host.
- **Obsidian-style full-project graph view** — a Search/Full-graph toggle in the Graph tab; Full graph renders every node/edge in the project (`GET /api/graph/full`, `IGraphTraversal.FullGraphAsync`), not just a hop-bounded neighborhood. Dense renders (>300 nodes) drop per-edge labels/arrows and use lighter physics — real project graph is 2483 nodes/2793 edges. "Show blast radius" on a clicked node jumps into the focused search view. Live-verified.
- **Codemem-style hybrid pack re-ranking refinements** — kind-based ranking bonus (decision/feature/bugfix prioritized) in `HybridScorer.ApplyMemoryTypeBonus`, plus query-intent detection (`QueryIntent`: pending-work/recall keyword routing) in `ContextPackBuilder`/`ContextEngine`.
- **Embedding cache cross-provider invalidation** — `Embedding` is now keyed by `(ContentHash, Provider)` instead of `ContentHash` alone; switching embedding providers no longer risks reusing a stale cross-provider vector.
- **Call-graph extraction fix** — tree-sitter `Calls` queries only matched bare-identifier invocations (`Foo()`), never member-access calls (`this.Foo()`, `obj.Foo()`, all LINQ) or method-group references (`.Select(Foo)`) — real symbols showed zero callers despite genuine usage. Fixed across C#/JS/TS/Python parsers.
- **Docker container → host Ollama networking** — `OllamaHostFallbackHandler` detects running-in-container and probes `host.docker.internal`/`172.17.0.1` as fallbacks when the configured host is unreachable. Confirmed live that this specific Rancher-Desktop-on-Windows setup still doesn't have a working candidate (its `host-gateway` maps both fallbacks to the same unreachable IP) — bare-metal remains the only verified-working path; the mitigation is real but doesn't fully close this environment's gap.
- **Microsoft.Extensions.AI provider migration** — `Context.Providers`' `ILlmProvider`/`IEmbeddingProvider` implementations now wrap `IChatClient`/`IEmbeddingGenerator<string, Embedding<float>>` (OllamaSharp, Anthropic.SDK, official OpenAI SDK) instead of hand-rolled HTTP calls; the app-facing interfaces are unchanged. Option registration refactored to match: `ProjectSettingsService` layers appsettings defaults → DB → `.claude/context-platform.local.json`; `Program.cs` builds `HybridScoringOptions`/`HybridSearchOptions`/`ContextPackOptions` from `IConfiguration`; `HybridScorer`/`HybridSearchEngine`/`ContextPackBuilder` accept an `IOptionsMonitor<T>` overload so retrieval-tuning config can change without a restart (provider *selection* — noop/ollama/openai — still can't hot-swap, see the item below). Live-verified: a real `/api/search` hit went through the new `OllamaEmbeddingProvider` end-to-end.
- **Options pattern refactor + ILlmProvider/IEmbeddingProvider removal** — `Program.cs`'s ~230 lines of hand-rolled `IConfiguration` parsing replaced with `services.Configure<T>(section)` (Retrieval options) and dedicated setup classes (`ContextProvidersOptionsResolver`, `OllamaOptionsSetup : IConfigureNamedOptions<OllamaOptions>` — unifies what used to be two near-duplicate Ollama options classes into one, registered as named "embedding"/"chat" instances). `ILlmProvider`/`IEmbeddingProvider` and every implementation deleted — they were thin wrappers around `IChatClient`/`IEmbeddingGenerator<string, Embedding<float>>` that added nothing not already exposed via `GetService<EmbeddingGeneratorMetadata/ChatClientMetadata>()`. Ollama-specific behavior (context-length retry, friendlier chat errors) survives as `OllamaEmbeddingGeneratorDecorator`/`OllamaChatClientDecorator` (`DelegatingEmbeddingGenerator`/`DelegatingChatClient` subclasses). Also removed `MemoryFile`/`MemoryRelation`/`MemorySymbol` (dormant, zero write call sites) with a migration dropping the tables. `Program.cs` is ~150 lines now, host wiring only.
- **Live settings reload — provider *selection* hot-swap** — `IEmbeddingGenerator<string, Embedding<float>>`/`IChatClient` are no longer a single process-wide singleton pair chosen once at startup; `Context.Application.Providers.ProjectProviderResolver` (`IProviderResolver`, in `Context.Providers.Abstractions`) resolves each project's own saved provider (`ProjectSettingsDto`, via `IProjectSettingsService`) fresh on every call, caching constructed clients by their resolved (provider, baseUrl, model) tuple rather than by project — two projects with identical Ollama config share one client; a project's own saved settings take effect on the very next call, no host restart. Every real consumer (`IndexingPipeline`, `LlmFileSummarizer`, `SqliteSearchIndex`, `EmbeddingLookupAdapter`/`IEmbeddingLookup`, `EmbedChunkJobHandler`, `LlmSessionSummarizer`, `LlmMemoryExtractor`, `SystemEndpoints`) now goes through the resolver instead of constructor-injecting a provider directly; `Context.Cli`/the process-default pair are unaffected (`AddContextProviders`'s own DI-registration-time construction, unchanged). OpenAI/Anthropic stay process-wide (no per-project key/model in `ProjectSettingsDto`) — only the provider *choice* and Ollama's own base URL/models are genuinely per-project. Found and fixed two more single-tenant bugs in the same neighborhood while tracing every consumer: `SessionEventSourceAdapter`/`ContextEngine.EndSessionAsync` both resolved "the current project" as `projects[0].Id` (whichever project happened to be first in the DB) instead of the session's actual owning project — silently broke session-end summarization/memory-extraction for any project that wasn't first (`EndSessionAsync` threw `KeyNotFoundException` before the job was even enqueued). `EndSessionAsync`/`ISessionSummarizer.SummarizeAsync`/`IMemoryExtractor.ExtractAsync`/`ISessionEventSource.GetEventsAsync` all gained an explicit `projectId` parameter; `GetProjectIdAsync` deleted as dead code. Live-verified: two fresh projects with different Ollama settings, same running process, `GET /api/system/status` reported each project's own provider correctly with zero restart between saves; ending a session on the third-created (non-first) project produced real `SummarizeSession`/`ExtractMemory` jobs (`Done`, no errors) instead of silently never enqueuing.
- **Vector store migration (Microsoft.Extensions.VectorData)** — `SqliteSearchIndex.VectorSearchAsync`'s brute-force cosine scan (decode+score every project chunk's embedding in C#) is now a real ANN index: `SqliteChunkVectorIndex` wraps `Microsoft.SemanticKernel.Connectors.SqliteVec`'s `SqliteCollection<Guid,TRecord>`, one collection per embedding provider (`chunk_vectors_{provider}`, since dimensionality is fixed per provider/model). The old `Embeddings` content-hash cache is untouched (still dedupes provider calls across identical content); the new index is a separate, minimal `(ChunkId, ProjectId, Vector)` structure joined back to `Chunks`/`Files` at query time, so a stale entry from a reindexed/deleted chunk is self-healing rather than needing proactive cleanup. A brand-new provider's collection backfills itself from the existing `Embeddings` cache on first creation. Package note: `Microsoft.SemanticKernel.Connectors.SqliteVec` 1.74.0-preview needs `Microsoft.Extensions.VectorData.Abstractions` pinned to `10.1.0`, not the newer `10.9.0` — letting it float compiles fine but throws `MissingMethodException` at runtime (binary-incompatible `VectorSearchOptions<T>` shape). Live-verified: a real query returned the same top hit/near-identical score as the old brute-force scan (0.8535 vs. 0.8534...), and a full reindex ran real `EmbedChunk` jobs through the new write path with zero failures.
- **Dashboard/Host → Context.Dashboard (esproj + SpaProxy) migration** — `apps/dashboard` moved to `apps/host/Context.Dashboard/context.dashboard.client` (as `context.dashboard.client.esproj`, wired into `ContextPlatform.slnx`); `apps/host/Context.Host` renamed+moved to `apps/host/Context.Dashboard/Context.Dashboard.Server` (namespace, csproj, Dockerfile, CI, deploy scripts, docs all updated — internal namespace kept `Context.Dashboard.Server` throughout, no `Context.Host` references left outside `.claude/worktrees`). `Context.Dashboard.Server.csproj`'s old MSBuild `Exec`-target (`BuildDashboard`/`CopyDashboardToWwwroot`) replaced with `Microsoft.AspNetCore.SpaProxy` (`SpaRoot`/`SpaProxyServerUrl`/`SpaProxyLaunchCommand` properties + `ASPNETCORE_HOSTINGSTARTUPASSEMBLIES` in `launchSettings.json`, `proxyConfig`/`src/proxy.conf.js` on the client's `serve` target) — matches the shape a fresh `dotnet new angular`-equivalent VS template produces (reference scaffold under `apps/host/Template/`, untracked). This is dev-inner-loop only: production no longer gets the Dashboard bundled into `wwwroot/` automatically by `dotnet publish` — Docker already built it independently (`Dockerfile`'s `dashboard-build` stage, unaffected), bare-metal Windows-service/systemd deploys now need an explicit `npm run build` + copy step first (see `deploy/README.md`). Live-verified end-to-end: `dotnet run` auto-launches `npm start` and both proxy directions work (backend root 302s to the dev server; the dev server's `proxy.conf.js` forwards `/health` etc. back to the backend).

## 📋 Planned (not started)

- **ModelContextProtocol.AspNetCore major version bump** — pinned to the `0.2.0-preview.3` this project started on; a `2.2.0` bump was tried alongside the AI-provider migration and reverted (unrelated scope, unverified API surface). Worth its own pass to check what changed in `AddMcpServer()`/`WithHttpTransport()`/`MapMcp()` before upgrading.
- **Vector index proactive cleanup** — `SqliteChunkVectorIndex` has no delete-on-reindex step (see its own remarks): a chunk replaced or removed leaves its vector-index row behind as harmless-but-accumulating cruft, filtered out at query time by the join back to `Chunks`. Fine at this platform's local-first scale; would need a real cleanup path (or a periodic sweep job) for a project with heavy reindex/delete churn.
- **Multi-tenant single host** — one Context.Dashboard.Server process serves every project instead of one systemd instance + port + bearer token per project (current model: `HostProjectContext` is a singleton bound to exactly one `ProjectId`/`ProjectRoot`/`BearerToken`/db at startup — see `deploy/install-systemd-service.sh`, one `context-platform@<name>.service` instance per project). Needs: request-scoped project resolution (bearer token → project, not process → project; each project keeps its own token, checked against a per-project store instead of one singleton value), a single shared `context.db` across every project (already true as of the `SharedDataLocation` move — the database now lives at one machine-level path, `Project` rows for every project already coexist in it; a per-request-resolved `DbContext`/connection replaces today's one-instance-per-project-root connection, which was the thing keeping each systemd instance pointed at its own file), indexing/file-watcher/job-queue instantiated per project rather than one global instance, and MCP tool default `projectId` resolved from the caller's token instead of `HostProjectContext`'s singleton. Discovered as a real gap 2026-09-03: two projects both defaulting to port 47923 meant only one's token/db was ever live; the other's requests silently authenticated against the wrong project. Not yet scoped into an implementation plan.
